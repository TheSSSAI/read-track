# 1 Overview

## 1.1 Diagram Id

SEQ-EP-001

## 1.2 Name

Asynchronous Event Processing for 'ReadingSessionLogged'

## 1.3 Description

After a reading session is successfully saved, a `ReadingSessionLogged` domain event is published within the backend. Multiple, independent handlers from different modules subscribe to this event and execute their own logic in a decoupled, asynchronous manner.

## 1.4 Type

🔹 EventProcessing

## 1.5 Purpose

To demonstrate the decoupling of business logic between modules (e.g., Reading and Engagement) and to handle side effects of a core action without impacting the initial request's performance.

## 1.6 Complexity

Medium

## 1.7 Priority

🔴 High

## 1.8 Frequency

OnDemand

## 1.9 Participants

- REPO-BE-MOD-READING
- REPO-BE-MOD-ENGAGEMENT
- REPO-BE-LIB-INFRA

## 1.10 Key Interactions

- The Reading module's service successfully saves a new `ReadingSession`.
- Before committing the transaction, it raises a `ReadingSessionLogged` event containing the session details.
- The MediatR library receives the event.
- MediatR dispatches the event to all registered `INotificationHandler`s for this event type.
- Handler 1 (in the Engagement module) updates the user's goal progress.
- Handler 2 (in the Engagement module) updates the user's daily/weekly reading streak.
- Handler 3 (in the Recommendations module) flags the user's profile as 'stale' for the next vector embedding job.
- The original database transaction is committed.
- The API response is returned to the user, without waiting for the handlers to complete.

## 1.11 Triggers

- A `ReadingSession` entity is successfully created.

## 1.12 Outcomes

- Multiple downstream business processes are triggered from a single action.
- Modules remain loosely coupled, improving maintainability.
- The user receives a fast API response.

## 1.13 Business Rules

- Event handlers should be idempotent.
- Failure in one event handler should not prevent other handlers from executing.

## 1.14 Error Scenarios

- A single event handler fails and logs an error, but the main transaction has already committed.

# 2.0 Details

## 2.1 Diagram Id

SEQ-EP-001

## 2.2 Name

Implementation of Asynchronous, In-Process Event Handling for ReadingSessionLogged

## 2.3 Description

This sequence details the technical implementation of an in-process, asynchronous event processing pattern using MediatR's INotification. When a ReadingSession is created and saved within a database transaction, a 'ReadingSessionLogged' domain event is published. This publication is non-blocking, allowing the initial API request to complete and return a response immediately. MediatR then dispatches this event to multiple, independent handlers running on background threads, effectively decoupling downstream business logic (like updating goals and streaks) from the core transaction.

## 2.6.0.0 Notes

### 2.6.1.0 Content

#### 2.6.1.1 Content

Key Design: The initial API response (Step 7) is sent BEFORE the asynchronous event handlers (Steps 8-10) have completed. This ensures the user-facing request is fast, while side-effects are processed in the background.

#### 2.6.1.2 Position

bottom

#### 2.6.1.3 Participant Id

*Not specified*

#### 2.6.1.4 Sequence Number

7

### 2.6.2.0 Content

#### 2.6.2.1 Content

Transactional Boundary: The main database transaction commits at Step 5. Any database operations within the event handlers (e.g., Step 8.1) run in their OWN, separate transactions. This is a crucial aspect of eventual consistency in this pattern.

#### 2.6.2.2 Position

bottom

#### 2.6.2.3 Participant Id

*Not specified*

#### 2.6.2.4 Sequence Number

5

### 2.6.3.0 Content

#### 2.6.3.1 Content

Idempotency: All handlers must be designed to be idempotent. It's possible for an event to be processed more than once in a complex recovery scenario. Logic should check if the action has already been performed.
