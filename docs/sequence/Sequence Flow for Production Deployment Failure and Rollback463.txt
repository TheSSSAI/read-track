# 1 Overview

## 1.1 Diagram Id

SEQ-RF-001

## 1.2 Name

Production Deployment Failure and Rollback

## 1.3 Description

During a production deployment, a critical failure is detected by automated health checks or a CloudWatch alarm. The CI/CD pipeline automatically initiates a rollback to the previous stable version of the infrastructure and application by re-deploying the last known good state via AWS CDK.

## 1.4 Type

🔹 RecoveryFlow

## 1.5 Purpose

To minimize downtime and user impact in the event of a faulty deployment, as per the contingency plan in REQ-TRN-001.

## 1.6 Complexity

High

## 1.7 Priority

🚨 Critical

## 1.8 Frequency

OnDemand

## 1.9 Participants

- GitHub Actions
- AWS CDK

## 1.10 Key Interactions

- A new backend version is deployed.
- Post-deployment health checks fail or a CloudWatch alarm for 5xx errors is triggered.
- The CI/CD pipeline detects the failure status.
- The pipeline automatically triggers a rollback step.
- The rollback step executes an AWS CDK command to redeploy the previous stable version of the infrastructure and container images.
- The public status page is updated to inform users of the issue.
- An alert is sent to the development team to investigate.

## 1.11 Triggers

- A critical failure (failed health check, CloudWatch alarm) is detected immediately following a production deployment.

## 1.12 Outcomes

- The system is restored to its last known good state.
- The impact on end-users is minimized.
- The faulty deployment is prevented from causing a prolonged outage.

## 1.13 Business Rules

- The CI/CD pipeline must support automated rollback.
- Clear criteria must be defined for what constitutes a critical deployment failure.

## 1.14 Error Scenarios

- The rollback process itself fails.
- The issue is not resolved by the rollback, indicating a problem with a dependency.

## 1.15 Integration Points

- AWS APIs

# 2.0 Details

## 2.1 Diagram Id

SEQ-RF-001-IMPL

## 2.2 Name

Automated Production Deployment Rollback via CI/CD Pipeline

## 2.3 Description

This sequence details the automated recovery flow when a production deployment introduces a critical failure. A post-deployment monitoring step within the GitHub Actions workflow detects a CloudWatch alarm (e.g., spike in 5xx errors). The workflow's error handling job is triggered, which updates the public status page, checks out the previous stable git tag, and executes 'cdk deploy' to restore the last known good infrastructure and application state, thereby minimizing user impact and downtime.

## 2.6.0.0 Notes

### 2.6.1.0 Content

#### 2.6.1.1 Content

The 'failure' trigger is critical. It's not just a failed command, but a semantic failure detected by monitoring (e.g., CloudWatch Synthetics canary tests or metric alarms) in a dedicated 'smoke test' or 'monitor' stage of the deployment workflow.

#### 2.6.1.2 Position

top

#### 2.6.1.3 Participant Id

CICD-GITHUB-ACTIONS

#### 2.6.1.4 Sequence Number

4

### 2.6.2.0 Content

#### 2.6.2.1 Content

The rollback mechanism relies on the immutability of git tags to ensure the exact code of the previous stable version is deployed. The CDK stack must be designed to handle rollbacks gracefully (e.g., avoiding destructive changes).

#### 2.6.2.2 Position

bottom

#### 2.6.2.3 Participant Id

AWS-CLOUDFORMATION
