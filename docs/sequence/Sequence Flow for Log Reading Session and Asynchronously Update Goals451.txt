# 1 Overview

## 1.1 Diagram Id

SEQ-FF-001

## 1.2 Name

Log Reading Session and Asynchronously Update Goals

## 1.3 Description

A user records a reading session for a book. The system saves the session details and then publishes an asynchronous, in-process event. Decoupled handlers subscribe to this event to update the progress of all relevant active goals without blocking the initial user request.

## 1.4 Type

🔹 FeatureFlow

## 1.5 Purpose

To enable the core reading tracking functionality (REQ-TRK-001) and provide real-time feedback on goal achievement (REQ-GOL-001) in a scalable, decoupled manner.

## 1.6 Complexity

Medium

## 1.7 Priority

🚨 Critical

## 1.8 Frequency

OnDemand

## 1.9 Participants

- REPO-FE-MOBILE
- REPO-BE-HOST

## 1.10 Key Interactions

- User selects a book and enters progress (page number/time spent).
- Client sends the session data to the backend API.
- The MOD-READING service validates and saves the ReadingSession entity within a transaction.
- An in-process event (`ReadingSessionLogged`) is published via MediatR before the transaction commits.
- A handler in the MOD-ENGAGEMENT service consumes the event.
- The handler fetches the user's active goals and updates their progress values.
- The transaction is committed, and a success response is sent to the client.
- Client UI reflects the new session and fetches updated goal progress.

## 1.11 Triggers

- User submits a form to log a reading session.

## 1.12 Outcomes

- A new ReadingSession record is created.
- The progress of the user's active goals is updated.
- The UI reflects the new session and updated goal progress.

## 1.13 Business Rules

- Reading sessions can only be logged for items on the 'Currently Reading' shelf.
- Goal progress must update automatically after a session is logged.

## 1.14 Error Scenarios

- Invalid progress is entered (e.g., page number lower than previous).
- The event handler for goal updates fails; the main transaction should still succeed, but the error must be logged.

# 2.0 Details

## 2.1 Diagram Id

SEQ-FF-001

## 2.2 Name

Implementation: Log Reading Session and Asynchronously Update Goals

## 2.3 Description

A comprehensive technical sequence for logging a user's reading session. The process utilizes a CQRS pattern with a `LogReadingSessionCommand` to handle the initial synchronous write operation. Upon successful persistence of the session, an in-process, asynchronous domain event (`ReadingSessionLogged`) is dispatched via MediatR. This event is consumed by a separate, decoupled handler in the Engagement module to update the user's goal progress. This event-driven approach ensures the initial user request is highly responsive and resilient to failures in secondary, non-critical operations like goal updates.

## 2.6.0.0 Notes

### 2.6.1.0 Content

#### 2.6.1.1 Content

CRITICAL IMPLEMENTATION DETAIL: The `UpdateGoalProgressOnReadingSessionLoggedHandler` must swallow any exceptions it encounters after logging them. This is a business requirement to ensure that a failure in updating goals (a secondary concern) does not cause the primary action of logging a reading session to fail. This makes the system more resilient.

#### 2.6.1.2 Position

bottom-right

#### 2.6.1.3 Participant Id

REPO-BE-MOD-ENGAGEMENT

#### 2.6.1.4 Sequence Number

6

### 2.6.2.0 Content

#### 2.6.2.1 Content

The Domain Event Dispatcher pattern is used here. Events are collected on domain entities and dispatched by a DbContext interceptor only after the primary transaction has been successfully committed to the database. This ensures that event handlers do not operate on data that might be rolled back.
