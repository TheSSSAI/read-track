# 1 Overview

## 1.1 Diagram Id

SEQ-SI-001

## 1.2 Name

Fetching and Caching CMS Content

## 1.3 Description

The application fetches curated content (e.g., reading tips) from a headless CMS (Contentful). This content is cached at two levels: on the backend in Redis to reduce API calls to the CMS, and on the client in Isar to provide offline access.

## 1.4 Type

🔹 ServiceInteraction

## 1.5 Purpose

To decouple curated content from application code and deliver it efficiently, as per REQ-TIP-001 and REQ-VOC-001.

## 1.6 Complexity

Medium

## 1.7 Priority

🟡 Medium

## 1.8 Frequency

OnDemand

## 1.9 Participants

- REPO-FE-MOBILE
- REPO-BE-HOST
- Amazon ElastiCache for Redis
- Contentful

## 1.10 Key Interactions

- User navigates to the 'Tips' section.
- Client requests GET /api/v1/tips from the backend.
- Backend service first checks its Redis cache.
- On a cache hit, cached data is returned immediately.
- On a cache miss, the backend calls the Contentful API to fetch the content.
- The backend receives the content, stores it in Redis with a TTL, and returns it to the client.
- The client receives the data, displays it, and stores it in its local Isar database for offline viewing.

## 1.11 Triggers

- User accesses a feature that relies on CMS content.
- The cache for the CMS content expires.

## 1.12 Outcomes

- Curated content is displayed to the user quickly.
- Previously viewed content is available offline.
- The number of direct calls to the CMS API is minimized.

## 1.13 Business Rules

- A fallback behavior should serve stale content from the cache if the CMS is unavailable.
- Cache must be properly invalidated when content is updated in the CMS (e.g., via webhooks).

## 1.14 Error Scenarios

- The Contentful API is down, and the cache is empty.
- The Redis cache is unavailable.

## 1.15 Integration Points

- Contentful REST API (SI-004)
- Amazon ElastiCache for Redis

### 2.6.2.0.0.0.0.0 Content

#### 2.6.2.1.0.0.0.0 Content

Cache Invalidation Strategy: While this sequence describes the read path, cache invalidation is handled asynchronously. Contentful is configured with a webhook that triggers a secured endpoint on the backend API (e.g., POST /api/v1/cache/invalidate) upon content updates, which then deletes the 'cms:tips:all' key from Redis.

#### 2.6.3.1.0.0.0.0 Content

Stale-While-Revalidate: For enhanced resilience, the backend can be configured to serve stale data from Redis if the Contentful API is down, while asynchronously attempting to refresh the content in the background. This aligns with the business rule in REQ-REL-002.
