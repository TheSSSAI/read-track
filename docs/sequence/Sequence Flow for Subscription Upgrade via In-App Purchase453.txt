# 1 Overview

## 1.1 Diagram Id

SEQ-BP-001

## 1.2 Name

Subscription Upgrade via In-App Purchase

## 1.3 Description

A 'Free User' initiates an upgrade to the 'Premium User' tier. The process involves a native in-app purchase flow. The backend relies exclusively on a server-to-server webhook from the payment platform (Apple/Google) as the source of truth to update the user's subscription status.

## 1.4 Type

🔹 BusinessProcess

## 1.5 Purpose

To implement the core monetization strategy of the application by allowing users to purchase premium features, as defined in REQ-FRE-001.

## 1.6 Complexity

Critical

## 1.7 Priority

🚨 Critical

## 1.8 Frequency

OnDemand

## 1.9 Participants

- REPO-FE-MOBILE
- REPO-BE-HOST
- Apple App Store / Google Play Store

## 1.10 Key Interactions

- User taps 'Upgrade to Premium'.
- Client initiates the native in-app purchase flow.
- User confirms the purchase with the platform's billing system.
- The platform processes the payment and notifies the client.
- The platform sends a `SUBSCRIPTION_PURCHASED` server-to-server webhook to a dedicated endpoint on the backend.
- The MOD-MONETIZATION service validates the webhook's authenticity and token.
- The service idempotently processes the webhook, updating the user's record to 'Premium User' and setting the subscription expiry date.
- Client fetches the user's updated profile, unlocking premium features in the UI.

## 1.11 Triggers

- A user decides to upgrade their subscription.

## 1.12 Outcomes

- The user's account is successfully upgraded to the Premium tier.
- The user gains access to all premium features.
- A subscription record is created in the database.

## 1.13 Business Rules

- The backend must rely on server-to-server webhooks as the source of truth for subscription status to prevent client-side tampering.
- The webhook handler must be idempotent to handle potential duplicate events from the provider.

## 1.14 Error Scenarios

- The webhook from the platform is delayed or never arrives (a reconciliation job may be needed).
- The client-side confirmation succeeds, but the server-side update fails.

## 1.15 Integration Points

- Apple App Store / Google Play Billing webhooks (SI-006)

# 2.0 Details

## 2.1 Diagram Id

SEQ-BP-001

## 2.2 Name

Implementation: Subscription Upgrade via Server-to-Server Webhook

## 2.3 Description

Comprehensive technical sequence for a 'Free User' upgrading to the 'Premium User' tier. This business process involves the mobile client initiating a native in-app purchase, while the backend API (`REPO-BE-HOST`) exclusively trusts a server-to-server webhook from the payment platform as the authoritative source for updating the subscription status. This design ensures transaction integrity and prevents client-side fraud, directly implementing REQ-FRE-001.

## 2.6.0.0 Notes

### 2.6.1.0 Content

#### 2.6.1.1 Content

Client-side success is only provisional. The UI must show a 'Verifying...' or similar state until the user's profile is confirmed as 'Premium' from the backend. This prevents granting features before payment is verified server-side.

#### 2.6.1.2 Position

top

#### 2.6.1.3 Participant Id

REPO-FE-MOBILE

#### 2.6.1.4 Sequence Number

4

### 2.6.2.0 Content

#### 2.6.2.1 Content

Idempotency is CRITICAL. The webhook handler in MOD-MONETIZATION must use the unique transaction ID from the webhook to prevent processing duplicate events, which payment platforms may send.

#### 2.6.2.2 Position

right

#### 2.6.2.3 Participant Id

REPO-BE-HOST

#### 2.6.2.4 Sequence Number

7

### 2.6.3.0 Content

#### 2.6.3.1 Content

Webhook is the single source of truth for all subscription lifecycle events (purchase, renewal, cancellation, refund) as per REQ-FRE-001.
