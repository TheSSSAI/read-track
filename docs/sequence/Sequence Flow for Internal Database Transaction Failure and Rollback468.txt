# 1 Overview

## 1.1 Diagram Id

SEQ-EH-002

## 1.2 Name

Internal Database Transaction Failure and Rollback

## 1.3 Description

Handles a scenario where a multi-step operation involving several database writes fails partway through. The system ensures data integrity by rolling back the entire transaction, logs the critical error, and returns a graceful error message to the user.

## 1.4 Type

🔹 ErrorHandling

## 1.5 Purpose

To maintain data consistency and system stability in the event of internal data persistence failures.

## 1.6 Complexity

Medium

## 1.7 Priority

🔴 High

## 1.8 Frequency

OnDemand

## 1.9 Participants

- REPO-BE-HOST

## 1.10 Key Interactions

- User action triggers a complex command (e.g., completing a book, which updates the book status, updates goals, and creates a summary).
- The Application Service begins a database transaction.
- The service successfully writes the first entity (e.g., updates LibraryItem status to 'Read').
- The service attempts to write a second entity (e.g., update Goal progress) but encounters a database constraint violation or connection issue.
- The operation throws a DbUpdateException.
- A global exception handling middleware catches the exception.
- The database transaction is automatically rolled back by the DbContext's disposal.
- The middleware logs a critical error with the full exception details and correlation ID.
- The API returns a 500 Internal Server Error with a generic error message to the client.

## 1.11 Triggers

- A database error (e.g., constraint violation, deadlock, connection loss) occurs during a transaction.

## 1.12 Outcomes

- The database is left in a consistent state with no partial data committed.
- The user is notified that the operation failed.
- A high-severity alert is triggered for the development team.

## 1.13 Business Rules

- All multi-step write operations must be wrapped in a database transaction.

## 2.2 Name

Implementation: Internal Database Transaction Failure and Rollback

## 2.3 Description

Technical sequence for handling a failed multi-step database write operation. This diagram illustrates how a global exception handling middleware intercepts a DbUpdateException, ensures the transaction is rolled back by the DbContext, logs a critical error for observability, and returns a standardized 500 Internal Server Error to the client, thereby guaranteeing data consistency.
