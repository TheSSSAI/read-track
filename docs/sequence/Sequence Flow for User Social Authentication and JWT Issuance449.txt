# 1 Overview

## 1.1 Diagram Id

SEQ-AF-001

## 1.2 Name

User Social Authentication and JWT Issuance

## 1.3 Description

Handles user sign-up and login exclusively through third-party social providers (Google/Apple) via Auth0. Upon successful authentication, the backend validates the provider's token, creates a user record if one doesn't exist, encodes their role into a custom JWT, and issues a short-lived access token and a long-lived refresh token.

## 1.4 Type

🔹 AuthenticationFlow

## 1.5 Purpose

To securely authenticate users without managing passwords, creating a seamless and secure login experience as required by REQ-USR-001 and REQ-CON-001.

## 1.6 Complexity

High

## 1.7 Priority

🚨 Critical

## 1.8 Frequency

OnDemand

## 1.9 Participants

- REPO-FE-MOBILE
- REPO-BE-HOST
- Auth0
- Google/Apple Identity Provider

## 1.10 Key Interactions

- User taps 'Sign in with Google/Apple' on the mobile client.
- Client initiates the native OAuth/OIDC flow with the social provider.
- User authenticates with the provider, which returns an ID token to the client.
- Client sends the provider's ID token to the backend's /auth/social endpoint.
- Backend validates the token with Auth0 to ensure its integrity and authenticity.
- Backend queries its database to find the user or creates a new user record with a 'Free User' role.
- Backend generates and returns its own JWT access token (with role claims) and a secure refresh token to the client.
- Client securely stores the tokens for subsequent API calls.

## 1.11 Triggers

- User initiates a login or registration action.

## 1.12 Outcomes

- User is successfully authenticated within the application.
- A valid session is established, managed by JWTs.
- A user record exists in the primary database with the correct default role.

## 1.13 Business Rules

- Native email/password authentication is explicitly disallowed (TC-003).
- A user's role ('Free User' by default) must be determined and encoded as a claim into the JWT.

## 1.14 Error Scenarios

- The social provider token is invalid, expired, or fraudulent.
- The backend fails to connect to Auth0 for token validation.
- User revokes application permissions from their social provider account.

## 1.15 Integration Points

- Auth0 (SI-002)
- Google Sign-In / Sign in with Apple SDKs (SI-001)

SEQ-AF-001-IMPL

## 2.2 Name

Implementation: User Social Authentication and Custom JWT Issuance Flow

## 2.3 Description

Provides a detailed technical specification for the user authentication sequence using third-party social providers (Google/Apple) and Auth0. This sequence covers the client-side OAuth/OIDC flow, backend token validation, user record provisioning, and the generation of a custom JWT access token and refresh token. This implementation is designed to meet requirements REQ-USR-001 and TC-003.
